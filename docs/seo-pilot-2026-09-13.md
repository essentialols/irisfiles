The six-page experiment deployed 2026-09-09 depends on twelve pages staying as they are. Six are
treated, six are untreated comparisons, and editing *either* set now destroys the comparison it was

### The export that would unblock the rest of this work

A human with Search Console access to the `irisfiles.com` property needs to produce:

- Property: `irisfiles.com` (state whether it is the domain property or the URL-prefix property).
- Report: Performance, **Search type: Web**.
- Periods: the latest complete 28-day window, and the immediately preceding complete 28-day window.
  Record the exact start and end dates of both.
- Breakdown: **by query AND by page** (the query/page relationship, not sitewide averages).
- Columns: impressions, clicks, CTR, average position.
- Filters: keep country and device filters *identical* across the two periods, and record what they were.
- Also useful: the past three months at page level, to see trend direction rather than two points.

Caveat to carry into any analysis: Search Console anonymizes rare queries, so the query export is
never a complete record of non-branded searches. Treat query-level sums as a floor.

Keep any export outside this public repo. Suggested location: `~/.project-state/irisfiles-seo/`.

### Selection rule actually applied

With no first-party query data, the documented "positions 8 to 30 with meaningful impressions" rule
could not be evaluated for any page. So selection fell back to a single defensible criterion:

> Select a page where a **provable defect in the page's own content** was found by comparing the page
> text against the implementation, on a tool that is confirmed working.

`/avi-to-webm` qualified on exactly that basis, independent of ranking data. The remaining slots
require the export, because "which page is at position 8 to 30 with real impressions" is not
answerable from anything on this machine.

## Verified claims and their evidence

Every product and privacy claim added to a page traces to one of these. Nothing below is from
general knowledge about the formats.

| Claim now on a page | How it was established |
|---|---|
| Output is VP8 video and Vorbis audio in WebM | `js/vidconv-engine.js:33-48` args `-c:v libvpx -crf 30 -b:v 1M -c:a libvorbis -q:a 4`, then confirmed on a real output file with system `ffprobe`: container `matroska,webm`, video `vp8`, audio `vorbis` |
| Quality settings are fixed and not adjustable | The engine has `applyQualityToArgs`, but `js/vidconv-ui.js` never passes an `opts` argument, so it is unreachable from this page |
| One file at a time, no batch | `#file-input` has no `multiple` attribute, and `js/vidconv-ui.js` takes `Array.from(files)[0]`. Confirmed twice in the browser: Chromium rejects a multi-file `setInputFiles`, and a synthetic two-file drop still leaves one file queued |
| 10-minute duration limit is enforced | `MAX_DURATION = 600` checked in `js/vidconv-ui.js` before conversion |
| No file size limit; 200MB warning is advisory | `WARN_VIDEO_SIZE` is used only for a non-blocking notice. Grep for a hard cap in the video path returns nothing, while the same grep does find the real 100MB constants in `js/converter.js` and `js/compress-audio-engine.js`, which proves the pattern works and the absence is real |
| Audio survives conversion | No `-an` flag anywhere in the path, and `ffprobe` reports `vorbis` audio in the output of an AVI fixture that had an mp3 track |
| Conversion failure message wording | Quoted from source, then observed in the browser by feeding a truncated AVI |
| Files are not uploaded during conversion | 46 recorded request events in an instrumented run, all `GET`, none with a request body, no service worker, no WebSocket, and the only cross-origin traffic was four FFmpeg.wasm files from `cdn.jsdelivr.net` |
| The tool is **not** offline-capable | Reloading with `cdn.jsdelivr.net` blocked caused the conversion to fail. Stated plainly on the guide rather than left to be inferred from "runs in your browser" |

### Limitations we did not paper over

- The network observation covers **one browser (headless Chromium 148), one local build (commit
  `5799cd8`), one flow**. It is not a measurement of the production deployment, and the guide says so
  in those words.
- Absence of a POST is not proof that no data left the page. The guide says this too, rather than
  converting a clean network log into a privacy guarantee.
- The CDN-blocked test was a single-host route interception, not a real offline test. It was recorded
  as a finding, not as a passed offline check.
- The worked-example timings (roughly 800ms for a 3 second, 128x96 clip) came from 2 to 3 runs on a
  contended machine with no load control. They are an order of magnitude, not a benchmark, and are
  deliberately **not** quoted on the page as a performance promise, because a synthetic 128x96 clip
  tells a real user nothing useful about their own file.

## Measurement and review checklist

Nothing here has been deployed, so no SEO outcome has been observed and none is claimed.

**Primary outcome:** growth in reported non-branded Google Search clicks to `/avi-to-webm` and
`/verify-local-file-conversion`, stated alongside the limitation that Search Console anonymizes rare
queries and so undercounts non-branded demand.

**Supporting measures:** clicks and impressions; position on a consistently filtered set of priority
queries; CTR read together with position, country and device rather than alone; and actual published
external references, verified by loading the page.

Search metrics measure search. They do not establish that anyone completed a conversion. No
analytics were added for this work and none should be.

Weekly, once deployed, and it should take a few minutes:

1. Confirm both pages are still indexed and the canonical Google reports is the one we set.
2. Pull clicks, impressions, CTR and position for the two pages with identical filters each week.
3. Check whether the priority queries moved, rather than whether the sitewide average moved.
4. Note any outreach state change, with the evidence that justifies it.

**Checkpoint at week 6 after deployment** and **again at week 12**. Decide, do not drift:

- If several selected pages improve, pick the next small evidence-backed batch from the shortlist.
- If impressions rise but clicks do not, inspect the queries, the positions and the search snippet
  before writing more content. The title and description are the cheaper fix.
- If movement is unclear, check indexing and query fit first. Assume a crawl or intent mismatch
  before assuming the page needs more words.
- If outreach draws little engagement, improve the asset or the recipient selection before sending
  more messages. Volume is the last lever, not the first.
