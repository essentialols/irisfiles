How to verify that a file converter does not upload your files

Plenty of online converters say your files never leave your browser. That claim is easy to make and, unusually for a privacy claim, it is something you can check yourself in about ten minutes using tools already built into your browser. This page shows you how, and is equally honest about what the check does not prove.

You do not need to trust IrisFiles to use this. The method works on any converter, including ours.

Before you start: pick a file you can afford to lose

Use a sample file whose contents would not matter if a stranger read them. A throwaway photo, a generated test clip, a document with nothing real in it. This matters because of an obvious trap: if the tool does upload your file, then testing with a sensitive document is how you find out, and by then the file has already been sent. Never run this test for the first time with something private.

The demonstration

  1. Open developer tools before loading the converter. Press F12, or Ctrl+Shift+I on Windows and Linux, or Cmd+Option+I on macOS. Go to the Network tab. In Safari you first need to enable the Develop menu in Settings, under Advanced. The inspector only records what happens while it is open, so open it first.
  2. Load the converter page and watch what arrives. With the Network tab recording, load the page. Everything you see now is the application being delivered to you: the HTML document, stylesheets, scripts, fonts, and for heavier tools often a WebAssembly binary of a few megabytes. Get a feel for this baseline so that anything new stands out later.
  3. Make sure you can see Method and Size. Most browsers show these columns by default; if not, right click the column headers and enable them. The method tells you whether the browser was sending or asking, and the size tells you how much.
  4. Add your file and convert it. Keep watching the list. This is the moment that matters. If a tool uploads your file, it has to transmit those bytes, and a transmission of that size is hard to hide from the panel that is recording every request.
  5. Read the requests. Look for any POST, PUT or PATCH. Look for any request whose uploaded payload is in the same ballpark as your file. Click anything suspicious and open its Payload or Request tab to see what was actually sent. A converter doing the work locally will usually show only GET requests, all of them fetching its own code and assets.
  6. Check the quieter routes. Requests are not the only way out. In the Application panel, under Service Workers, check whether one is registered, since a service worker can make requests of its own. Back in the Network tab, filter by WS to show WebSocket connections, which carry data as a stream rather than as discrete requests. Neither is sinister on its own, but both are worth knowing about.

Not all network activity is suspicious

This is where most people get stuck, because a page that is busy on the network looks alarming even when nothing is wrong. The useful question is not whether traffic happened, but which direction it went and what it contained.

Ordinary and harmless:

  • The application itself. HTML, CSS and JavaScript have to reach your browser somehow.
  • A large WebAssembly download. Serious in-browser processing, such as video encoding, means shipping a real codec to your machine. A multi-megabyte .wasm file is the engine arriving, not your file departing.
  • Fonts, icons and stylesheets, often from a CDN.
  • Requests that continue after conversion, if they are fetching assets rather than sending payloads.

Worth a closer look:

  • A request carrying a body of roughly your file's size.
  • A POST that appears at the moment you press convert.
  • A WebSocket that opens when you add a file.
  • A conversion that fails when you are offline but is described as fully local. That combination suggests the work is happening somewhere else.

A genuinely local converter has a recognisable signature: a burst of downloads while the page and its engine load, then near silence while your machine does the work.

What this test does not prove

An honest method has to state its limits, and this one has real ones.

  • It covers one tool, one browser, one version, one moment. A clean result for one converter says nothing about the next page on the same site, or about the same page after its next deployment.
  • No POST is not the same as no data leaving. Data can also leave through a WebSocket, a service worker, a beacon, or a GET request with information encoded into the URL. The check makes the common case visible; it does not close every route.
  • It cannot see inside an encrypted payload it did not capture, and it only shows the paths you actually exercised. A different file type or an error path might behave differently.
  • Local processing is not the same as working offline. These get conflated constantly. A tool can do every computation on your device and still need the network to fetch its own code.
  • It says nothing about server logs. Requesting any page reveals your IP address and the time to the server and its CDN. That is how the web works, and it is a separate question from whether your file was transmitted.

What the test does give you is a specific, checkable observation to replace a marketing claim. That is a genuine improvement over taking a company's word for it, and it is worth doing even though it is not proof.

What we observed on IrisFiles

We ran exactly this check against our own AVI to WebM converter, and we are reporting the provenance so you can judge it rather than take it on faith.

  • What was tested: a local development build of this site, served from localhost, at commit 5799cd8.
  • Browser: headless Chromium 148.0.7778.96, driven by Playwright 1.60.0.
  • Date: 13 September 2026.
  • Method: every network request was recorded programmatically from before the page loaded until the converted file was downloaded, using a synthetic 3 second AVI test clip with an audio track.

In that run we recorded 46 request events. All of them were GET. None carried a request body. No service worker was registered, and no WebSocket was opened. The only requests to a third party were four files from cdn.jsdelivr.net, which make up the FFmpeg WebAssembly engine that performs the conversion. The video file itself was not sent anywhere.

The limits stated above apply to our own test as much as to yours. This was one browser, one flow, and a local build. It is not a measurement of the production site you are reading right now, and we are not going to present it as one. If it matters to you, run the check yourself against this page. That is the point of writing it down.

One related finding, since it cuts against us: when we reloaded the page with cdn.jsdelivr.net blocked, the conversion could not run. The processing is local, but fetching the engine is not, so this is not an offline tool. We would rather say that plainly than let "runs in your browser" quietly imply something it does not.

Common questions

Does the absence of POST requests prove my file was not uploaded?

No. It is good evidence and it rules out the most common way a file would be sent, but it is not proof. Data can leave a page through a WebSocket, a service worker, a beacon, or a GET request with the data packed into the URL. A single inspection also only covers the one path you exercised. Treat a clean network log as a strong signal, not a guarantee.

The converter downloaded several megabytes. Does that mean it sent my file somewhere?

Not by itself. Direction matters more than size. Downloading a large WebAssembly binary is the application arriving on your machine, which is the opposite of your file leaving it. Check whether the large transfer is a response being downloaded or a request body being uploaded, and check the request method.

Does a local conversion mean the site works offline?

Not necessarily, and the two claims are often confused. A tool can do all its processing on your device while still needing the network to fetch its own code. IrisFiles is an example: conversion happens locally, but the video engine is fetched from a CDN the first time you use it, so a freshly loaded page with the CDN blocked cannot convert. Only believe an offline claim if you tested it with the network actually disabled.

Can I trust a privacy claim just because the source code is public?

Public source makes a claim checkable, which is worth a lot, but the code in a repository is not necessarily the code a site is serving you right now. Reading the source tells you what the project intends. Watching the network tells you what your browser actually did. The two together are much stronger than either alone.

Does this test prove the site keeps no record of my visit at all?

No, and no site can honestly claim that. Loading any page tells the server and its CDN that a request came from your IP address at a particular time. That is ordinary web hosting, and it is separate from whether the contents of your file were transmitted. This test is about your file, not about the fact that you visited.
